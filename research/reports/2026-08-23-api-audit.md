# API audit — the real limit, condition pricing, and the 16k plan (2026-08-23)

## The headline correction: the limit is 20,000/day, not 200,000

**200,000 is the Business plan at $99/mo. We are on the API plan at $9.99/mo.**
Verified live against the docs' rate-limit table today:

| Plan | Price | Daily credits | Per-minute calls |
|---|---|---|---|
| Free | $0 | 100 | 60 |
| **API (ours)** | **$9.99** | **20,000** | **60** |
| Business | $99 | 200,000 | 500 |
| Enterprise | $300 | 1,000,000 | 1,000 |

This matters more than a factor of ten looks: a 16,468-card plan sized against
an imagined 200k budget fits comfortably. Against the real 20k it does not fit
in a day, and it can never be a *daily* job. Planning against the wrong number
would have produced a job that 429s partway through every morning.

- **Reset window:** the daily allowance resets at **00:00 UTC**. The per-minute
  limit clears within 60 seconds. Those are different clocks and `Retry-After`
  distinguishes them.
- **Per-endpoint?** No. One shared credit pool. Cost varies by *data requested*
  per card (basic 1, +1 history, +1 eBay, +1 Cardmarket), not by endpoint.
- **Prepaid credits exist** on paid plans — they don't expire, don't reset, and
  are drawn on automatically instead of returning 429. That is the escape hatch
  if a backfill overruns.

## Our actual consumption: 272 credits/day — 1.4%

Not "137 calls". Two corrections in one number:
- **Billing is on the requested `limit`, not on calls or results returned.** A
  default request costs 50 credits because `limit` defaults to 50.
- Our only daily caller is `fetch-sealed-crosscheck.mjs`: **136 reviewed
  entries at `limit=2` = 272 credits.** The other four PPT scripts
  (build-crosscheck-map, extend-crosscheck-map, fetch-singles-enrichment,
  verify-watchlist-prices) are manual tools and are not on the schedule.

**Headroom: ~19,700 credits/day unused.**

**Not verified:** the dashboard itself, which is behind Tyler's login. These are
the published tier limits. If the account carries prepaid credits or a custom
cap, only the dashboard shows it — though `X-RateLimit-Daily-Remaining` comes
back on every response, so one authenticated call would confirm the live balance.

## Condition pricing: YES — the full ladder

Not inferred. Verbatim from `research/eval-samples/ppt-cards-history-RAW.json`,
`prices.variants` on Umbreon VMAX:

```json
"Holofoil": {
  "Near Mint":         { "price": 112.64, "listings": null, "lastUpdated": "2026-08-17T00:00:00.000Z" },
  "Lightly Played":    { "price": 89.91,  "listings": null, "lastUpdated": "2026-08-17T00:00:00.000Z" },
  "Moderately Played": { "price": 67.14,  "listings": null, "lastUpdated": "2026-08-17T00:00:00.000Z" },
  "Heavily Played":    { "price": 50.74,  "listings": null, "lastUpdated": "2026-08-03T00:00:00.000Z" },
  "Damaged":           { "price": 39.38,  "listings": null, "lastUpdated": "2026-08-13T00:00:00.000Z" }
}
```

Billed `{"total":2,"breakdown":{"cards":1,"history":1},"costPerCard":2}`.
Cross-keyed by **printing AND condition**, so a Reverse Holo LP is its own
figure. **Both an NM index and an LP index are buildable.**

**The catch is cost, not capability.** The ladder only appears with
`includeHistory=true`. The same endpoint without it returns a single key:

```json
"Holofoil": { "Near Mint Holofoil": { "price": 113.22, ... } }
```

So NM alone is 1 credit/card; anything below NM is 2.

**One real limitation:** `listings` is `null` for every condition. We get
condition **prices**, never condition **supply** — so a depth or Buy-Pressure
read can never be split by condition. Worth knowing before anyone promises it.

## The plan for all 16,468 cards

The batching answer is better than per-card. A `setId` query **with no
limit/offset returns the entire set in one response, billed once** at set size ×
per-card cost — the per-request caps (200 basic / 100 with history / 25 with
both) do not apply. Minute cost is `min(30, ceil(cards/10))` per call.

Our catalogue is **16,468 cards across 130 sets** (largest: swshp 304, me2pt5
295, sv4 266).

| | NM only | Full ladder (NM/LP/MP/HP/DMG) |
|---|---|---|
| credits/card | 1 | 2 |
| **total credits** | **16,468** | **32,936** |
| fits in one 20k day? | **yes** | no — **2 days** |
| calls | 130 | 130 |
| minute-units | 1,700 of 60/min | 1,700 of 60/min |
| **wall clock** | **~29 min** | **~29 min** |
| on Business (200k) | 1 day | 1 day |

**The backfill is easy. The refresh is the real constraint.** A one-time full
ladder is two days and half an hour of API time. But **keeping it current daily
is impossible on this tier** — 32,936 credits against a 20,000 ceiling. Options,
cheapest first:
1. **Rotate**: refresh half the catalogue each day (~16.5k credits/day, inside
   budget). Every card is at most 48h stale.
2. **Tier the refresh**: daily for the few hundred cards anyone watches, weekly
   for the long tail. Matches how the data is actually read.
3. **Business at $99/mo** makes daily refresh trivial — but per Tyler's own
   recorded trigger, a paid tier is a "before the first dollar" decision, and
   the licensing question is tied to it.

**And the part worth saying plainly:** 15,727 of those 16,468 cards **already
have a price**, free, from pokemontcg.io's bundled TCGplayer block — captured by
the catalogue ingest at zero PPT cost. So "122 priced singles → sixteen
thousand" has, for market price, largely already happened. What PPT actually
buys is the **condition split** — the thing pokemontcg.io does not have at all,
and the thing the LP index needs.
